# ТЗ на дизайн «Большого КСО» (1080×1920, портрет)

**Назначение документа.** Это требование-логика для генерации дизайна в Claude Code. Документ описывает не «как нарисовать красиво», а *по каким правилам принимать каждое дизайн-решение*. Любой экран, компонент и размер должны выводиться из принципов раздела 3. Если решение нельзя обосновать одним из принципов — оно лишнее.

**Источник.** Текущее КСО: `INNO_Clouds_Kiosk`, разрешение **1024×1366 (портрет)**, версия 1.0.8.
**Цель адаптации.** Большое напольное КСО, экран **1080×1920 (портрет, 9:16)**, пользователь стоит.

---

## 1. Что есть сейчас (фиксация текущего КСО)

Поток текущего киоска (фастфуд — шаверма / горячие блюда / напитки):

1. **Idle / возврат внимания.** Диалог «Продолжить заказ? — Вы ещё с нами? — Сброс через N сек — Да / Нет». Таймаут бездействия сбрасывает заказ.
2. **Тип получения.** Экран «Как вы хотите получить заказ?» → две опции: **Здесь** / **С собой**.
3. **Меню.** Вертикальный рельс категорий (Горячие блюда, Салаты, Завтраки, Холодные напитки, Горячие напитки, Шаверма, Фирменная шаверма, Донеры, Роллы, Закуски, Соус) + сетка карточек товара (фото + название + цена, напр. «Эспрессо · 89 ₽»).
4. **Корзина.** Постоянный итог внизу («0 ₽»), переход к оформлению.
5. **Оплата и подтверждение** (стандартный хвост сценария КСО).

Главные сущности, которые переносим: *тип заказа → категории → карточка товара → модификаторы → корзина → оплата → номер заказа*.

---

## 2. Геометрия перехода 1024×1366 → 1080×1920

| Параметр | Текущее | Большое | Вывод для дизайна |
|---|---|---|---|
| Ширина | 1024 | 1080 | Почти не меняется (+5,5%). Горизонтальную раскладку **не перестраивать**. |
| Высота | 1366 | 1920 | +40,6%. **Весь прирост — по вертикали.** |
| Соотношение | ~3:4 | 9:16 | Экран стал заметно «длиннее» и уже относительно высоты. |

**Ключевой вывод:** это не «растянуть всё пропорционально». Лишнюю высоту нельзя раздавать равномерно — её надо отдать туда, где это снижает когнитивную нагрузку и сокращает движение руки: больше видимых карточек без скролла, крупнее цели, явная нижняя зона действий. Ширину контента держим близко к текущей, чтобы строка чтения и размер карточек оставались привычными.

## 3. Фундамент: 4 принципа → правила (ядро ТЗ)

Под каждым принципом — *правила*, которые Claude Code обязан соблюдать. «Экономия движения» здесь не отдельная цель, а следствие принципов.

### 3.1 Ясность / минимизация когнитивной нагрузки — Krug, «Don't Make Me Think»
Пользователь не должен думать — только действовать. Экран самоочевиден.

Правила:
- **Один экран — одна задача и один очевидный следующий шаг.** На каждом экране ровно одно главное действие, визуально доминирующее.
- **Никакого «расшифровывания».** Текст кнопок — глагол + объект («Добавить в корзину», «Оплатить 540 ₽»), а не «ОК»/«Далее» без контекста.
- **Убирать, а не добавлять.** Любой элемент, не ведущий к заказу, — кандидат на удаление. Декор не конкурирует с контентом за внимание.
- **Сильная визуальная иерархия:** на любом экране взгляд за <1 сек находит (1) где я, (2) что выбрать, (3) как продолжить.
- **Постоянство.** Положение шапки, рельса категорий, итога/CTA не «прыгает» между экранами.

### 3.2 Соответствие ментальной модели
Интерфейс ведёт так, как человек уже ожидает (по аналогии с кассой/меню/приложениями доставки).

Правила:
- **Порядок шагов = порядок в голове:** тип заказа → выбор блюд → проверка корзины → оплата → получить номер. Не нарушать и не перепрыгивать.
- **Категории — слева/в начале, товары — в основной области, корзина — справа/снизу как «поднос».** Это привычная модель меню.
- **Цена и итог всегда на виду** — пользователь в любой момент знает «сколько уже».
- **Прогресс читается:** видно, на каком шаге находишься и сколько осталось.
- **Слова пользователя, а не системы:** «С собой / Здесь», «Добавить», «Оплатить», без техножаргона.

### 3.3 Закон Фитца + закон Хика
Фитц: время до цели тем меньше, чем цель **крупнее и ближе**. Хик: время решения растёт с числом вариантов — **меньше опций за раз**.

Правила (с учётом стоящего пользователя у высокого экрана):
- **Крупные цели.** Минимальный тач-таргет **96×96 px** (≈12–14 мм). Главные кнопки (CTA, «+/–», «Добавить») — **от 140 px по высоте**.
- **Близко к руке.** Все основные действия — в нижней-средней зоне досягаемости (см. раздел 4). Верх экрана 1920 px — только для пассивной информации, не для кнопок, которые нужно жать часто.
- **Достаточные зазоры.** Между соседними тач-целями — **≥24 px**, чтобы исключить ложные нажатия (тоже Фитц: «промах» дорог).
- **Мало вариантов за раз (Хик).** На шаге выбора типа заказа — 2 опции. В рельсе категорий показывать ограниченный набор, остальное — скроллом, а не «стеной». На карточке товара — группировать модификаторы, не вываливать всё сразу.
- **Главная кнопка — самая большая и контрастная** на экране; альтернативы — заметно тише.

### 3.4 Обратная связь и предотвращение ошибок
Система подтверждает каждый засчитанный шаг и не даёт совершить ошибку.

Правила:
- **Мгновенный отклик на касание** (<100 мс): нажатие меняет вид (press-state), добавление в корзину — видимая анимация + обновление счётчика/итога.
- **Подтверждение результата, а не только действия:** «Добавлено», бейдж количества на корзине, рост суммы.
- **Обратимость вместо запретов:** легко изменить количество и удалить позицию; деструктивные действия (очистить корзину) — с подтверждением.
- **Предотвращение тупиков:** обязательные модификаторы нельзя пропустить; кнопка «Оплатить» неактивна, пока корзина пуста, и явно показывает почему.
- **Безопасный idle:** диалог «Вы ещё с нами?» с понятным таймером и крупными «Да/Нет»; сброс не происходит молча.
- **Ошибки — на языке решения:** «Нет связи с оплатой. Попробуйте ещё раз / Позовите сотрудника», а не код ошибки.

### 3.5 «Экономия движения» как следствие
Не самостоятельный принцип, а результат 3.1–3.4: меньше шагов (ясность), привычный путь (модель), близкие крупные цели и мало выбора (Фитц+Хик), отсутствие откатов из-за ошибок (обратная связь). **Метрика:** минимальное число касаний и минимальный путь руки от «выбрал блюдо» до «оплатил».

## 4. Зоны экрана 1080×1920 (досягаемость стоящего пользователя)

Высокий напольный киоск: низ экрана у пояса, верх — выше уровня глаз. Делим высоту 1920 px на функциональные зоны:

| Зона | Диапазон по Y | Назначение | Можно ли класть частые кнопки |
|---|---|---|---|
| **A. Шапка / контекст** | 0–280 px | Логотип, «где я» (шаг, категория), номер заказа. Пассивная информация. | Нет (далеко тянуться) |
| **B. Контент** | 280–1400 px | Категории + карточки товара / тело экрана. Скролл здесь. | Вторично |
| **C. Зона действий (главная)** | 1400–1750 px | CTA, «Добавить», «+/–», «Оплатить», итог. **Самая удобная зона руки.** | **Да — приоритет** |
| **D. Системная полоса** | 1750–1920 px | Доступность (понизить интерфейс), язык, помощь, version. | Редкие действия |

Правила зон:
- **Каждое решающее действие экрана живёт в зоне C.** Это прямое применение Фитца к вертикали 1920 px.
- **Дублировать корзину/итог в зоне C как липкую панель** — чтобы «сколько» и «оплатить» всегда под рукой.
- **Кнопка доступности «опустить экран»** (режим для невысоких пользователей / колясок) — сдвигает зоны B–C вниз. Обязательна на большом экране.

## 5. Сетка, размеры, типографика (числовые требования)

Базис: модульная сетка 8 px. Все размеры кратны 8.

**Поля и сетка**
- Внешние поля контента: **48 px** слева/справа.
- Колонки карточек товара: **2 колонки**. Расчёт: контент 1080 − 48 − 48 = 984 px; при зазоре 48 px ширина карточки = (984 − 48) / 2 = **468 px**. Не делать 3 колонки — фото станут мелкими, пострадает ясность.
- Вертикальный зазор между карточками: **32 px**.

**Размеры целей (Фитц)**
- Карточка товара: ширина 468 px, высота **≥460 px** (фото + название + цена + кнопка «+»).
- Кнопка «+» на карточке: **≥120×120 px**, правый нижний угол карточки.
- Главный CTA (нижняя панель): высота **≥160 px**, ширина — на всю ширину контента.
- Степпер количества «– N +»: каждая кнопка **≥120×120 px**.
- Пункт рельса категорий: высота **≥112 px**, активный — выделен заливкой и контрастом.
- Минимум для любой кликабельной зоны: **96×96 px**; зазор между целями **≥24 px**.

**Типографика** (стоящий пользователь, дистанция ~50–70 см)
- Название товара: **36–40 px**, полужирный.
- Цена: **40–48 px**, акцентный цвет, самый заметный текст карточки.
- Заголовок экрана: **56–64 px**.
- Текст кнопки CTA: **40–44 px**.
- Вторичный текст / описание: **28–32 px** (не мельче 28 px).
- Контраст текста к фону: **≥ 4.5:1** (WCAG AA); для крупного — ≥ 3:1.

**Цвет и состояния**
- Один акцентный цвет для главного действия. Остальные кнопки — нейтральные/контурные.
- Обязательные состояния каждой кнопки: обычное, **press (нажато)**, disabled, выбрано. Press-state виден сразу при касании.

## 6. Поэкранные требования

Для каждого экрана: задача, одно главное действие, как применяются принципы.

**6.1 Idle / заставка.** Задача — пригласить начать. Главное действие — крупное «Нажмите, чтобы заказать» (по центру зоны B–C). Карусель/промо допустимы, но не мешают одному очевидному входу.

**6.2 Тип получения.** «Как вы хотите получить заказ?» — **2 крупные карточки-кнопки** (Здесь / С собой) с иконкой и подписью, каждая ≥ 700×500 px, в зоне B–C. Хик: только 2 варианта. Без «назад в никуда».

**6.3 Меню (ядро).**
- Слева рельс категорий (липкий, скролл вертикальный), справа 2 колонки карточек.
- Активная категория подсвечена; скролл товаров синхронизирован с категорией (ментальная модель «оглавление»).
- Каждая карточка: фото, название, цена, кнопка «+». Тап по карточке → детали/модификаторы; тап по «+» → быстрое добавление (если нет обязательных опций).
- Липкая нижняя панель корзины в зоне C: «Корзина · N поз · Сумма ₽» + «Перейти к оплате».
- Обратная связь: при «+» — анимация в корзину, рост счётчика и суммы.

**6.4 Карточка товара / модификаторы.** Фото сверху, название, цена, группы опций. Обязательные группы помечены и блокируют добавление, пока не выбрано (предотвращение ошибок). Степпер количества крупный. Внизу зоны C — «Добавить N за СУММУ ₽». Закрытие — крупный крестик в зоне досягаемости, не в самом верху.

**6.5 Корзина / проверка.** Список позиций с фото, количеством (степпер прямо в строке), ценой, удалением (свайп или кнопка с подтверждением). Итог крупно. Главный CTA «Оплатить СУММУ ₽» — зона C, максимальный размер/контраст. «Добавить ещё» — вторичная, тихая кнопка.

**6.6 Оплата.** Понятная инструкция «Приложите карту / телефон», крупная иконка, статус в реальном времени (ожидание → успех/ошибка). Ошибка — с понятным следующим шагом и «Позвать сотрудника». Никаких ручных вводов реквизитов в дизайне.

**6.7 Подтверждение.** Крупный **номер заказа** (главный объект экрана), статус «Оплачено», что дальше («Ожидайте на табло»). Авто-возврат на idle через таймаут с возможностью «Новый заказ».

**6.8 Idle-диалог возврата.** «Вы ещё с нами?» + видимый таймер + крупные «Да/Нет» в зоне C. Не сбрасывать заказ без явного исхода.

## 7. Чек-лист приёмки (self-check для Claude Code)

Дизайн принимается, только если на **каждом** экране выполнено:

- [ ] Одна задача, одно доминирующее действие, очевидный следующий шаг (3.1).
- [ ] Текст действий — глагол+объект, без жаргона и «ОК/Далее» без контекста (3.1, 3.2).
- [ ] Порядок шагов совпадает с ожиданием пользователя; цена/итог всегда видны (3.2).
- [ ] Главные кнопки в зоне C (Y 1400–1750), не в верхних 280 px (3.3, §4).
- [ ] Тач-цели ≥ 96×96 px, главные ≥ 140 px высоты, зазоры ≥ 24 px (3.3, §5).
- [ ] На шаге выбора — минимум вариантов; длинные списки скроллятся, а не «стеной» (3.3).
- [ ] У каждой кнопки есть press/disabled/selected; добавление даёт видимый отклик (3.4).
- [ ] Обязательные опции нельзя пропустить; деструктив — с подтверждением; idle безопасен (3.4).
- [ ] Контраст ≥ 4.5:1; минимальный кегль ≥ 28 px (§5).
- [ ] Есть режим доступности «опустить экран» (§4).
- [ ] Лишняя высота 1920 отдана под крупность целей и видимость, а не под пустоту/равномерное растяжение (§2).

---

## 8. Как использовать этот документ в Claude Code

1. Передать файл как контекст/требование к задаче «сгенерируй дизайн экранов большого КСО 1080×1920».
2. Просить генерировать **по одному экрану**, каждый раз указывая: задачу экрана, главное действие, зону C для CTA, и прогонять §7.
3. Для каждого решения требовать обоснование ссылкой на принцип (3.1–3.4). Нет обоснования → убрать элемент.
4. Держать §4 (зоны) и §5 (размеры) как жёсткие constraints — это не «рекомендации», а границы.

> Принцип над всем: **меньше думать — больше действовать.** Каждый пиксель экрана 1080×1920 работает на то, чтобы путь от «зашёл» до «оплатил» был коротким, привычным и без ошибок.
